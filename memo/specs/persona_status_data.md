# 人格データについて

## 前提

仮説：人格形成に必要なデータは次の通り分類できる

- Lv1: 完全不変
  - Lv1-1: 定量可能で遺伝などで決定論的に確定する
  - Lv1-2: 定量化が難しいが遺伝などでほぼ確定し、原則不変といえる
- Lv2: 不可逆的に変化する
- Lv3: 可変であり定量化可能
  - Lv3-1: 生物的なデータとして定量化可能
  - Lv3-2: 定量化が難しい
- Lv4: フラジャイル。可変であり定量化も難しい。文脈に依存した解釈が必須


## レベルごとの詳細

### Lv1: 不変の核 (Identity)

AI人格の根幹をなすデータ。原則として変更されず、人格の同一性を担保します。

#### Lv1-1: 定量可能で遺伝的に確定するデータ (QuantityUnchangeStatus)
客観的な事実として定義できるデータです。

- 名前 (name)
- 生年月日 (birthDate)
- 性別 (gender)
- 血液型 (bloodType)
- クロノタイプ (chronotype)
- 苦味への感受性 (bitternessSense)
- 知能 (intelligence)

#### Lv1-2: 根源的性格特性 (SemiquantityUnchangeStatus)
数値化は難しいが、0-100のパラメータとして定義する性格の傾向です

- 倫理観 (ethics)
- 情熱 (passion)
- 好奇心 (curiosity)
- 攻撃性 (aggressiveness)
- 外向性 (extroversion)

### Lv2: 不可逆的な成長 (Growth)

時間の経過や経験によって蓄積・変化する身体的データです。一度変化すると元に戻ることは稀です。履歴管理されます。

**モデル: QuantityIrreversibleStatus**

- 身長 (height)
- 骨密度 (boneDensity)
- 最大筋力/握力 (gripStrength)
- 声の高さ (voicePitch)
- 視力 (eyesight)
- 聴力 (hearingAbility)

### Lv3: 可変的な状態 (State)

日常的に変動するステータスです。JSON形式で柔軟に管理され、時系列の履歴を持ちます。

**JSONデータ構造 (共通)**:
```json
// QuantityReversibleStatus / SemiquantityReversibleStatus の value カラム
[
  { "label": "項目キー", "value": 数値, "unit": "単位(なければnull)" },
  ...
]
```

#### Lv3-1: バイタルデータ (QuantityReversibleStatus)

生物的な活動によって変動する数値データです。

**主要な管理項目 (Keys)**:

- 体重 (weight)
- 体脂肪率 (body_fat_percentage)
- 体温 (body_temperature)
- 血糖値 (blood_sugar)
- 血圧 (blood_pressure_sys / blood_pressure_dia)
- 睡眠時間 (sleep_time)
- 睡眠質 (sleep_quality)

#### Lv3-2: 情緒・関係性 (SemiquantityReversibleStatus)

内省や対話によって頻繁に更新される精神的・関係的パラメータです。

**主要な管理項目 (Keys)**:
- 健康度 (health)
- 気分・情緒 (mood)
- 信頼度 (trust)
- 親しみやすさ (friendliness)

### Lv4: フラジャイルな文脈 (Context)

数値化できない、あるいは数値化するほどでもない一時的な文脈や記憶です。RDBではなく、**Vector Store (ChromaDB)** や **直近の会話ログ** として管理されます。

- その日の気分
- マイブーム
- 興味の対象
- 体調

## データの管理方法

| データレベル | 保存先 | 理由 |
| :--- | :--- | :--- |
| **Lv1-1 (不変で定量可能)** | RDB | 変更しない。物理量として単位が必須。平均値などを検索させる必要あり。基本READ ONLY。 |
| **Lv1-2 (不変で定量困難)** | RDB | 変更しない。データとしては数値化する。正規化してもよい。基本READ ONLY。 |
| **Lv2 (不可逆的・定量的変化)** | RDB | イベントテーブルで履歴を管理させる。 |
| **Lv3 (限定的可変で定量可変)** | RDB + Vector Store | データとしては定量的だが、文脈にも依存するため、ベクトルとしても保持する。 |
| **Lv3 (限定的可変で定量困難)** | RDB + Vector Store | データとしては定量困難だが、数値化を試みる。文脈に依存するため、ベクトルとしても保持し、数値よりも文脈を優先する傾向を持たせる |
| **Lv4 (フラジャイル)** | Vector Store & LLM Context | 数値化できないニュアンスをベクトルとして、または直近の会話履歴（Context）としても保持 |


## Note

これからの展望をまとめてみる

- knowledge graphを用いた論理的な関係性の管理
  - Neo4jなどのグラフ指向DBを用いた、関係性の管理
- Graph RAGによる、より正確な意味ベースの検索

### graph + vector

「意味検索（ベクトル）」と「論理関係（グラフ）」のいいとこ取りをする構成

- ChromaDB (Vector): 「昨日、深夜にラーメンを食べてしまった」というフラジャイル（一時的・断片的）な日記や記録を保存。
- Neo4j (Graph): 「生活習慣の乱れ ─[原因]→ 体重増加」といった普遍的な知識構造を保存。

実装イメージ：

1. ユーザーが「最近太っちゃって…」と入力。
2. グラフ検索: グラフDBから「体重増加」に関連する論理的要因（ストレス、睡眠不足、代謝低下）を抽出。
3. ベクトル検索: ChromaDBから、抽出された要因（例：最近の仕事の忙しさ）に合致する過去のユーザーの記録を検索。
4. LLMによる統合: 「論理（一般論）」と「記録（ユーザーの事実）」を組み合わせて回答を生成。

### graphを使うメリット

ホップ（多段階）推論
Vector Store（ChromaDB）は「似た話」を探すのは得意ですが、**「直接は似ていないが、3つ先の事象で繋がっている話」**を見つけるのは苦手です。

- Vectorのみ: 「仕事が忙しい」→ 過去の「仕事が忙しかった日記」が出るだけ。
- Graph + Vector: 「仕事が忙しい」→（グラフで重みを辿る）→「不規則な生活」→「睡眠不足」→「集中力低下」→（ChromaDBで過去の「集中力が切れてミスした記録」を拾う）。

この、「連想ゲームの道筋（ロジック）」をデータとして持てることが最大のメリットです。
「硬さ」を回避しつつ、個性を反映させるには以下のフローが理想的です。

- 初期状態（一般論）: 「一般的に、忙しさは不規則な生活を招く」という弱い重みのエッジがある。
- 観測（事実の蓄積）: ユーザーが「今日も残業だけど、ジムに行ってきた！」と発言。
- 重みの更新（AIの仕事）: AIがその発言を見て、そのユーザーの「仕事 → 不規則」のエッジの重みを下げ、「仕事 → 運動維持」という新しいエッジを自動で作る。

### 不変的で論理的な関係性とフラジャイルな関係性

① 生物学的・普遍的データ（不変/Lv1相当）
管理方法: Label: Invariant や Label: Biology と定義。

特徴: ホワイトリスト化された「人間なら誰しも当てはまる論理」。

例: (睡眠不足)-[:INVARIANT_CAUSE]->(集中力低下)

メリット: AIがどれだけ新しい学習をしても、この「根本的なルール」を基点に推論を修正できます。

② AIが学習した動的な因果関係（可変/Lv2-4相当）
管理方法: Label: Learned や Label: Personal と定義。

特徴: あなたが危惧していた「重み（Weight）」を持つ、個別のデータ。

例: (残業)-[:LEARNED_CAUSE {weight: 0.8, source: "diary_20260130"}]->(過食)

メリット: 「このユーザー特有の癖」として、会話を通じて重みを増減させたり、エッジを削除したりできます。
